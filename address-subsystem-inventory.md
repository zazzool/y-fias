## 1. Что делает подсистема сегодня

Адрес — обязательная часть карты вызова психиатрической неотложной помощи.
Подсистема закрывает шесть задач:

| Задача | Где реализовано | Состояние |
|---|---|---|
| Подсказки улиц при вводе | `addressService.suggest` + `streetDictionary` + DaData | работает |
| Проверка написания (опечатки, раскладка) | `addressService.validate` + `addressModel` | работает, в SPA не используется |
| Разбор и нормализация (дом, тип улицы) | `formatHouseCanonical`, `street_key`, `search_norm` | работает |
| Определение района и ПНД | `addressNeighbors` → Nominatim → DaData → таблица `pnds` | работает |
| Дедупликация и слияние адресов | `getOrCreate`, `mergeAddresses`, `addressModel` | работает частично |
| Хранение и поиск | таблица `addresses`, триграммные индексы | работает; дефект §8.1 исправлен 17.08.2026 |

**Ключевой принцип, выработанный практикой (17.08.2026):** система
подсказывает, но никогда молча не подменяет введённое пользователем. Нарушение
этого принципа было причиной жалобы, с которой начался разбор (§8.2).

## 2. Модель данных

### 2.1. Таблица `addresses` (фактическая DDL с прода)

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | `text` PK | ключ; в API отдаётся как `_key` |
| `region` | `text` | код региона строкой: `77` Москва, `50` МО |
| `district` | `text` | район (для Москвы — район города, для МО — район области) |
| `street` | `text` | улица с типом: «Тверская улица». Вне Москвы — с контекстом в скобках: «Вишнёвая улица (СНТ Лесная поляна, Раменский р-н)» |
| `house` | `text` | номер дома как ввёл пользователь: `7к7`, `10с4`, `вл15А` |
| `building` | `text` | не используется (осталось от импорта) |
| `flat` | `text` | не используется: квартира живёт в `calls.apartment` |
| `pnd_id` | `smallint` | номер ПНД, обслуживающего адрес |
| `organization` | `text` | официальное название учреждения по адресу |
| `lat`, `lon` | `double precision` | координаты — **заполнено 0 записей** |
| `settlement` | `text` | населённый пункт — заполнено 9 записей |
| `created_at` | `timestamptz` | |
| `full_address` | `text` **GENERATED ALWAYS** | «улица, дом»; до миграции 0050 подменялась организацией — см. §8.1 |

Выражение генерируемой колонки — после миграции `0050` (17.08.2026):

```sql
CASE
  WHEN house IS NOT NULL AND house <> '' THEN street || ', ' || house
  ELSE street
END
```

До `0050` первой ветвью стояло `WHEN organization <> '' THEN organization` —
название учреждения ПОДМЕНЯЛО адрес, и вызовы в учреждения не находились по
улице. Разбор и измеренный эффект — в §8.1.

Индексы: `addresses_pkey`, `idx_addresses_str_h` (UNIQUE на `street, house` —
на нём стоит `ON CONFLICT` в записи), `idx_addresses_house_num`,
`idx_addresses_street_key_trgm`, `idx_addresses_street_norm_trgm`,
`idx_addresses_full_address_trigram`, `idx_addresses_organization_trgm`
(добавлен `0050` — поиск по названию учреждения).

### 2.2. Сопутствующие таблицы

* **`pnds`** — 148 строк, колонки `id text`, `pnd smallint`, `dis text`.
  Отображение «район → номер ПНД». Соединяется по ТЕКСТУ района
  (`LEFT JOIN pnds ON pnds.dis = addresses.district`), поэтому расхождение в
  написании района (в т.ч. `ё`/`е`) рвёт связь.
* **`street_dictionary`** — 3028 строк, `id serial`, `full_name text UNIQUE`,
  `created_at`. Копилка названий улиц, выученных из ответов DaData. **Создаётся
  в рантайме** (`CREATE TABLE IF NOT EXISTS` внутри `addressService`), а не
  миграцией.
* **`address_corrections`** — 46 строк. Обучающая выборка модели исправлений:
  `wrong_str`, `wrong_h`, `correct_str`, `correct_h`, `source` (`merge`/`manual`),
  `count`, `created_at`, `updated_at`.
* **`orgs`** + **`org_addresses`** — справочник организаций и маски адресов для
  рантайм-сопоставления (`orgMatcher.ts`). Это **места назначения эвакуации**,
  их нельзя путать с `addresses.organization` (§8.4).
* Таблицы-снимки для откатов разметки: `address_org_snapshot`,
  `address_org_snapshot_0026/0027/0028/0034/0042/0044`.

5. **Координат нет ни у одного адреса.** Геометрических методов (ближайший

### 2.6. Функции PostgreSQL

```sql
-- 0026: ведущее число дома. «10к1» → 10, «7к7» → 7, «СЕМЬк7» → NULL
house_num(h text) RETURNS integer
  → NULLIF((regexp_match(COALESCE(h,''), '^\s*(\d+)'))[1], '')::integer

-- 0029: нормализация текста для поиска. ё→е, дефисы → пробелы,
-- прочие небуквенно-цифровые → пробел, схлопывание пробелов
search_norm(t text) RETURNS text

-- 0029: ключ улицы — без типа и без учёта порядка слов.
-- «улица Саляма Адиля» = «Саляма Адиля ул.» = «саляма адиля»
street_key(t text) RETURNS text
```

Список отбрасываемых типов улиц в `street_key` (важно: он **дублируется** в
TypeScript, см. §8.5): `ул, улица, ш, шоссе, пр, прт, пркт, проспект, пер,
переулок, пл, площадь, б, бр, бульвар, наб, набережная, прд, проезд, туп,
тупик, аллея, линия, кв, квартал, мкр, микрорайон`.

## 3. Серверные модули

Все пути от `web/ponp.psync.ru/`.

### 3.1. `server/domain/addressService.ts` — центральный сервис

Публичный интерфейс:

* `suggest(query, limit=10)` → `AddressSuggestion[]`. Сначала локальный
  справочник (мс), затем DaData, если локальных мало и запрос ≥ 3 символов.
  Ответы DaData **дописываются в локальный справочник** в фоне (обучение).
  Результаты объединяются с дедупликацией и сортируются по score.
* `validate(str, h?)` → `ValidationResult` со статусом
  `valid | warning | unknown`. Слои: латинская раскладка → смешанные алфавиты →
  точное совпадение со справочником → нечёткое совпадение (порог 0.65,
  предлагается исправление) → наличие улицы в `addresses` → «не найдено».
  **Никогда не исправляет сама**, только предлагает. Формат дома проверяется
  мягко (не пусто, есть цифры, не `0`, не 5+ цифр).
* `getOrCreate({str, h, reg, dis, pnd, skipValidation})` → `ResolvedAddress`.
  Порядок: канонизация дома → точное совпадение `street+house` → нормализованное
  совпадение (§8.2) → создание с обогащением. Запись через
  `INSERT … ON CONFLICT (street, house) DO UPDATE`, где непустые значения
  заполняют пустые, но не перетирают заполненные.
* `resolveDistrict(str, h)` → `{dis, pnd, source: 'neighbors'|'geo'|'none',
  candidates[]}`. Источники по порядку: консенсус соседних домов → Nominatim →
  DaData; при разногласии соседей возвращает кандидатов для уточнения человеком.

Экспортируемые функции разбора:

* `formatHouseCanonical(raw)` — канонический номер дома. Убирает пробелы и
  точки; `корпус|корп → к`, `строение|строен|стр → с`, `владение|влад → вл`;
  буквы приводит к верхнему регистру, но `к`/`с` перед цифрой или буквой
  оставляет строчными. «7 корпус 7» → `7к7`, «10 строение 4» → `10с4`,
  «владение 15» → `вл15`.
* `normalizeStreetForCompare(str)` — отбрасывает тип улицы регулярками
  `STREET_TYPE_RE`, убирает скобки и пунктуацию.
* Приватное: `_findExactAddress`, `_findNormalizedAddress`,
  `_enrichExistingAddress`, `_getEnrichmentData`, `_resolveDistrictPnd`
  (сопоставление района с `pnds` в три попытки: точно → регистр → `ё`/`е`).

**Важно про ПНД:** при создании адреса `pnd_id` пишется **только если его явно
передал пользователь**. Автоматическая подсказка ПНД по району намеренно не
подмешивается в запись (комментарий в коде: ПНД — поле, которое должен
устанавливать человек).

### 3.2. `server/domain/addressNeighbors.ts` — вывод района по соседям

Чистый модуль без БД, введён 17.08.2026. Вход — номер дома и список соседей
`{house, district, pnd_id}` с той же улицы; выход — район, ПНД, уровень
уверенности и список кандидатов.

Правила весов:

* совпало ЧИСЛО дома (корпуса/строения у дома-родителя) — вес **100**;
* та же чётность номера — `max(0, 50 − 4·|Δ|)`;
* противоположная сторона улицы — `max(0, 20 − 4·|Δ|)` (чётная и нечётная
  стороны шоссе могут быть в разных районах — подтверждено данными: 181 улица);
* `confidence = 'high'`, если доля лидера ≥ 0.8 И (вес ≥ 100 ИЛИ ≥ 2 согласных
  соседей); иначе `'low'` и кандидаты отдаются на выбор.

ПНД внутри района выбирается по наибольшему суммарному весу.

### 3.3. `server/domain/streetDictionary.ts` — локальный справочник улиц

Три источника с приоритетом: статический seed (`server/data/moscow-streets-seed.ts`,
≈600 записей) → таблица `addresses` → таблица `street_dictionary`.
In-memory индекс с префиксными ключами (2 и 3 символа), TTL 5 минут,
дедупликация загрузок.

Поиск в четыре слоя со скорингом: точное совпадение (100 + бонусы за тип и
населённый пункт) → префикс (80 + бонусы) → подстрока (60) → нечёткое
(30 + сходство·30; расстояние Левенштейна ≤ 2 при ratio ≥ 0.6, либо биграммный
Dice ≥ 0.65 для строк от 5 символов).

Разбор запроса умеет: населённый пункт в скобках, тип улицы префиксом или
суффиксом, `TYPE_ALIASES` (≈30 сокращений: `ул`, `ул.`, `пр-кт`, `б-р`, `наб.` …).

Обучение: `learn()` и `learnFromDaData()` дописывают названия в память и в
`street_dictionary`.

### 3.4. `server/domain/addressModel.ts` — модель исправлений

Учится на слияниях адресов: «неверный» вариант → «верный». 46 обучающих записей.
Шесть слоёв предсказания с убывающей уверенностью:

1. точное совпадение `wrong_str||wrong_h` (уверенность 85 + 3·count, ≤ 99);
2. без учёта регистра (80 + 2·count);
3. **извлечённые правила трансформации** — из пар «было/стало» вычисляются
   замены (`ул.` → `улица`) по общему префиксу/суффиксу и по словам;
   применяются top-20 правил с count ≥ 2;
4. нормализованное совпадение (65 + 2·count);
5. совпадение только по улице, дом сохраняется пользовательский (55 + 2·count);
6. нечёткое по биграммам ≥ 0.75 (35 + сходство·40).

Кэш в памяти, TTL 3 минуты, инвалидация при обучении.
**Модель в SPA не используется** — вызывается только через `utilsService.predictAddress`.

### 3.5. `server/services/dadadata.ts` — внешние источники

Два независимых источника:

* **DaData suggestions** (бесплатный endpoint, round-robin по нескольким
  токенам из `NUXT_DADADATA_SUG_TOKENS`): подсказки улиц с ограничением
  `locations: [77, 50]`, `locations_boost: [77]`, границы `from_bound/to_bound:
  street`. Есть фолбэк на платный endpoint (`/clean`) с `X-Secret`.
  Таймаут 4 с. LRU-кэш в памяти: 2000 записей, TTL 3 минуты.
* **OSM Nominatim** — прямое геокодирование ради района: сначала
  «улица, дом, Москва, Россия», затем без дома. Таймаут 5 с, retry 1 с задержкой
  1100 мс (лимит 1 запрос/с), свой `User-Agent`.

Функции: `getStreetSuggestions`, `resolveFullAddress`, `getAddressCoords`,
`resolveDistrictDaData`, `formatStreetSuggestion`.

Особенности, введённые 17.08.2026:

* если гранулярный запрос по улицам ничего не дал (ввод «от посёлка»:
  «СНТ Лесная поляна, Вишнёвая»), выполняется свободный поиск без границ, из
  результатов берутся только предложения с заполненной улицей;
* `formatStreetSuggestion` формирует подпись с контекстом ДО РАЙОНА ОБЛАСТИ:
  «Вишнёвая улица (СНТ Лесная поляна, Раменский р-н)» — одноимённые СНТ разных
  районов различимы прямо в выпадающем списке;
* `resolveFullAddress` разбирает такую подпись обратно (скобки → «Московская
  обл, <контекст>, <улица>») и для области кладёт в `a_dis` **район области**
  (`area`), а не город.

Нормализация названий районов Москвы: `DISTRICT_ALIASES` (Бауманка → Басманный,
Канатчиково → Донской, Нагатинская пойма → Нагатинский Затон, Чертаново →
Чертаново Северное) плюс срезание префикса/суффикса «район»/«р-н».

### 3.6. `server/domain/orgMatcher.ts` — организации по адресу

Рантайм-сопоставление адреса с маской из `org_addresses`; использует
`formatHouseCanonical` и свой `normalizeStreetKey` (список токенов обязан
совпадать со `street_key` в SQL — §8.5).

### 3.7. Вспомогательные утилиты

## 5. Поиск по адресу

Адресная ветвь `smart-search.post.ts` — самая нагруженная. Её текущая форма
получена после четырёх переписываний, и правила ниже соблюдать обязательно:

* сравнение дома — **по числу** через `house_num()`, не строкой;
* сравнение улицы — по `street_key()` (без типа, без порядка слов);
* сначала отбор по МАЛЕНЬКОЙ таблице с индексом (`addresses` — 10 тыс.,
  `patients` — 35 тыс.), только потом присоединение `calls` (92 тыс.);
* только ОПЕРАТОРЫ (`%`, `<%`, `%>`), а не функции: триграммный GIN ускоряет
  операторы, вызов `word_similarity(...) > 0.38` даёт Seq Scan;
* `JOIN LATERAL` по токенам вместо `EXISTS (SELECT … unnest)` — последний
  индекс не использует.

Замеренные последствия нарушений (из истории проекта): адресная ветвь
4582 мс → 186 мс; функция вместо оператора — 476 мс вместо 95 мс;
`EXISTS` вместо `LATERAL` — 1017 мс вместо 95 мс; сравнение дома строкой
находило 2 адреса из 59 и 223 вызова из 449.

**Правило на будущее:** правку поиска проверять `EXPLAIN (ANALYZE)`, а не на
вид SQL — обе ловушки выглядят безобидно и молча дают Seq Scan.

## 6. Интерфейс диспетчерской (SPA, `web/ponp4.psync.ru/`)

### 6.1. Поля адреса в карте вызова

Форма `app/pages/calls/edit/[key].vue`, блок «Адрес вызова (город, улица)»:

| Поле | Модель | Где хранится |
|---|---|---|
| Улица | `a_str` | `addresses.street` |
| Дом | `a_h` | `addresses.house` |
| Кв. | `a_ap` | `calls.apartment` |
| Подъезд | `a_en` | `calls.entrance` |
| Этаж | `a_fl` | `calls.floor` |
| Код | `a_c` | `calls.intercom` |
| Регион | `a_reg` | `addresses.region`, по умолчанию `77` |
| Район | `a_dis` | `addresses.district`, показывается подписью у метки |
| ПНД | `a_pnd` | `addresses.pnd_id`, показывается подписью у метки |
| Организация | `a_org` | `addresses.organization`, только чтение |

Заметьте: квартира, подъезд, этаж и код относятся к КАРТЕ, а не к адресу — один
адрес обслуживает много вызовов с разными квартирами.

### 6.2. Что происходит при вводе

1. **Подсказки улиц.** Компонент `SmartField`; запрос
   `POST /utils/streets {query, select: 0}`. Московские подсказки (регион 77)
   помечаются чипом «МСК» и идут выше, для остальных в подзаголовке показывается
   населённый пункт.
2. **Выбор улицы из подсказок** (`onStreetSelected`, задержка 150 мс) —
   `POST /utils/streets {query, select: 1}` дозаполняет `a_reg`, `a_str`, `a_dis`.
   Срабатывает только если значение есть в подсказках или в чипах истории —
   свободный ввод не трогается.
3. **Район и ПНД по улице И дому** (введено 17.08.2026; задержка 400 мс, защита
   от гонки ответов по счётчику запроса) — `POST /utils/address/district`.
   Если сервер вернул `dis` — подставляется; если вернул `candidates` — они
   показываются чипами «Район · ПНД ?», выбор за диспетчером. Номер дома код не
   меняет никогда.
4. **Чипы истории адресов** пациента (`addrChips`) — два самых частых адреса из
   предыдущих вызовов.
5. **Шаблоны адресов** (`PSelect type="orgs"`) — выбор учреждения заполняет
   `a_org`, `a_reg`, `a_dis`, `a_str`, `a_h` и обнуляет квартиру, подъезд, код.
6. **Адреса пациента.** Выбор пациента из подсказок переносит его адреса; если
   их несколько — открывается уточняющий диалог, по умолчанию подставляется
   адрес последнего вызова.
7. **Диалог «Редактировать адреса пациента»** (`AddressesDialog.vue`) — правка
   (`POST /admin/addresses`) и слияние (`POST /admin/addresses/merge`) с выбором
   основного адреса радиокнопкой.

### 6.3. Правила отображения организации

`app/utils/callOrg.ts` + `callOrg.spec.ts` (16 проверок). Организация размечена
НА АДРЕСЕ, но по одному адресу вызов может быть и в учреждение, и в квартиру
(Смольная, 5 — жилой дом, в котором находится ПНД № 4). Правило слоёное:

1. только типы «Неотложный» (0) и «Эвакуация» (2) — плановые инъекции, активы и
   платные это работа на дому;
2. эвакуация — показываем всегда;
3. неотложный — сначала ПОВОД: «м/э», «МЭ:», «эвакуация», «консультация»,
   «по путёвке», «госпитализация», «из ПНД», «в ПКБ», «каб» → показываем
   (повод важнее квартиры);
4. иначе смотрим квартиру: похожа на настоящую (число до четырёх знаков с
   необязательной буквой) → скрываем;
5. квартиры нет → показываем.

Последним правилом стоит «показать», потому что в СИЗО поводы не содержат слова
«консультация», а квартир там нет. Проверено на данных: из 759 неотложных
вызовов в СИЗО правило скрывает организацию у двух.

Название организации всегда показывается РЯДОМ с улицей и домом и **никогда
вместо них**: по «ГКБ № 67» не найти дом, по «Саляма Адиля, 2» не понять, что
это больница. Подстановка вместо адреса всплывала в коде трижды — при правках
проверять (и см. дефект §8.1).

### 6.4. Поле «Кв.» и вызовы в учреждения

Поле запирается при вызове в учреждение (`isOrgCallForm` — то же правило, но БЕЗ
учёта квартиры: опираться на неё значило бы рассуждать по кругу). Под полем
подсказка, что кабинет, отделение и корпус вносятся в «Примечания». Уже
введённая квартира при переходе карты в разряд организационных не теряется, а
дописывается в примечания.

Причина: в больницах в поле квартиры писали ЛИТЕРУ КОРПУСА («Г», «к Г», «кГ» —
у ГКБ № 67 таких 589 вызовов), отделение («отд. псо»), в ПНД — номер кабинета
(«каб 221»). Миграция `0040` привела накопленные данные к этому виду: 1848
вызовов, снимок `calls_apartment_snapshot_0040`. 52 неотложных вызова с
настоящими номерами квартир на смешанных адресах не тронуты.

### 6.5. Форма эвакуации и корпус

`confirmEvac()` собирает номер дома с корпусом как `${base}к${corpus}` — то есть
интерфейс сам порождает написания вида `7к5`. Отделение пишется в примечания
(раньше писалось прямо в поле квартиры). Контакты приёмного отделения
подсказываются по `a_str` + базовому дому (`/op/evac-contacts/suggest`) и
обучаются на подтверждении (`/op/evac-contacts/learn`).

### 6.6. Прочие места, где адрес виден

* список диспетчерской `operate.vue` — адрес и второй строкой район либо
  название организации;
* `RecentCallsTable.vue`, `PatientSummary.vue` — история пациента;
* `report.vue` — экранный отчёт;
* `calls/view/[key].vue` — readonly-просмотр карты;
* умный поиск `SmartSearch.vue` — задержка 300 мс, защита от гонки ответов по
  `requestId`, минимальная длина запроса.

## 8. Известные дефекты и ловушки

### 8.1. `full_address` подменял адрес названием организации — ИСПРАВЛЕНО 17.08.2026

**Что было.** Генерируемая колонка (§2.1) у 396 адресов с организацией равнялась
НАЗВАНИЮ УЧРЕЖДЕНИЯ, а «улица, дом» в ней не было вовсе. При этом ветвь
нечёткого поиска карт (`callRepository.getManyByAddress`) искала ТОЛЬКО по
`full_address`. Следствие: вызовы в учреждения по названию улицы не находились.

**Измеренный эффект (прод, до и после).** По запросу «саляма адиля» находилось
7 адресов, из них ни одного адреса ГКБ № 67; поиску было доступно **12 вызовов**.
После правки — 59 адресов (52 из них адреса учреждений) и **2 763 вызова**.

**Как исправлено.** Миграция `0050`: `full_address` стал чистым адресом —
`street || ', ' || house`. Название в колонку **намеренно не дописано**:
потребители добавляют его сами (`RecentCallsTable.vue` печатает `a_sa` и
дописывает ` · a_org`, `smart-search.post.ts` и `xls.ts` собирают строку
самостоятельно), и оно бы задвоилось — ровно это уже случалось в отчёте
(«ГКБ №67 · ГБУЗ «ГКБ № 67…»», разбор в `reportsService.ts`). Правило,
подтверждённое дважды: **поле адреса — всегда улица и дом, название выводится
отдельным полем, они не пересекаются.**

Чтобы не потерять поиск по названию учреждения, добавлен индекс
`idx_addresses_organization_trgm`, и оба запроса поиска спрашивают
`a.organization` отдельным условием (`%>` и `LIKE`). План проверен:
`BitmapOr` по двум триграммным индексам, Seq Scan нет. Поиск «гкб 67» находит
2 751 вызов.

Порядок выкладки был: сначала код, затем миграция — тогда окна с неработающим
поиском по названию не возникает.

Рядом, в другом запросе (около строки 1122), есть ветка с
`LOWER(a.street) LIKE …` — там поиск по улице работал и раньше.

> **Остались однотипные подмены в трёх местах.** Поле `a_sa` собирается
> «организация ВМЕСТО адреса» ещё в `callMapper.ts` и в двух `CASE` выражениях
> `server/api/calls/search.post.ts`. Это тот же класс ошибки; сейчас он влияет
> только на легаси-потребителей (`a_sa` из `mapCallRow` после миграции стал
> чистым адресом). Унифицировать стоит, но это отдельное решение: часть
> интерфейсов дописывает название сама, и слепая правка задвоит его.

### 8.2. Подмена номера дома при дедупликации — исправлено 17.08.2026

Симптом: диспетчер вводил дом `7к7`, а сохранялся другой номер; спасал только
ввод «СЕМЬк7» (карта 2610837). Причина: `_findNormalizedAddress` считала
совпадением равенство ВЕДУЩЕГО ЧИСЛА дома (`house_num`), и `7к7` приклеивался к
существующему `7к1`/`7` на той же улице. «СЕМЬк7» спасал потому, что у него нет
ведущего числа.

Исправление: совпадением считается только полное равенство канонической формы
(`formatHouseCanonical`): «7 к 7» = «7к7», но «7к7» ≠ «7к1» ≠ «7». Число дома
осталось лишь предфильтром кандидатов.

**Для нового сервиса это главный урок.** Число дома — инструмент ПОИСКА
кандидатов, но никогда не критерий тождества. Тождество — полный разобранный
номер: дом, корпус, строение, владение, литера.

### 8.3. Автоподстановка ПНД

`pnd_id` при создании адреса пишется только из явного пользовательского ввода;
подсказка по району в запись намеренно не подмешивается. Заполнено 1 684 адреса
из 10 694 (16%). Если новый сервис начнёт заполнять ПНД автоматически, это
изменит цифры в отчётах по ПНД — решение владельца, не техническое.

### 8.4. `addresses.organization` ≠ место эвакуации

`addresses.organization` отвечает на вопрос «что находится ПО АДРЕСУ ВЫЗОВА»;
`calls.evacuation_destination` → `orgs` — «куда увезли пациента». Смешение уже
приводило к тому, что в отчёте больница назначения печаталась сразу после адреса
и читалась как место вызова.

### 8.5. Дублирование правил нормализации в трёх местах

Список типов улиц и ключ улицы существуют:

1. в SQL — `street_key()` (миграция 0029);
2. в TypeScript — `normalizeStreetKey()` в `orgMatcher.ts`;
3. в TypeScript — `normalizeStreetForCompare()` + `STREET_TYPE_RE` в
   `addressService.ts`.

Списки токенов обязаны совпадать; расхождение даёт разный результат в
зависимости от того, кто сравнивал. В новом сервисе это должен быть ОДИН
источник правды.

### 8.6. Ловушки производительности

См. §5. Кратко: только операторы (не функции), `JOIN LATERAL` (не `EXISTS`),
отбор по малой таблице до присоединения `calls`, `EXPLAIN (ANALYZE)` обязателен.

### 8.7. Внешние зависимости и их пределы

* **Nominatim** — 1 запрос в секунду, публичный сервис без SLA; вызывается на
  каждый неизвестный адрес. Кэш всего 3 минуты — после перезапуска процесса
  греется заново.
* **DaData** — бесплатный endpoint подсказок, ключи в
  `NUXT_DADADATA_SUG_TOKENS` (round-robin ради лимитов); справочник ФНС не
  содержит части реальных строений. Платный endpoint настроен как фолбэк.
* **Координат в базе нет** — геометрические методы недоступны.
* Кэши DaData и Nominatim — in-memory на процесс, между экземплярами бэкенда не
  разделяются.

### 8.8. Что реализовано, но не используется

* `addressService.validate` — эндпоинт есть, SPA его не вызывает: предупреждения
  об опечатках и о латинской раскладке диспетчер не видит.
* `addressModel.predict` — модель исправлений обучается на слияниях, но её
  предсказания в форму не приходят.
* `addresses.lat/lon`, `building`, `flat`, `settlement` (9 записей) —
  фактически мёртвые поля.

1. **Разбор номера дома — ядро.** 6 036 адресов с кириллицей в номере, 2 034
   уникальных написания. Нужна структурная модель (дом, корпус, строение,
   владение, литера) с каноническим представлением для тождества и
   «человеческим» для показа. Ввод пользователя хранить как есть.
2. **Тождество адреса** — по разобранным компонентам, а не по числу дома
   (§8.2) и не по строке целиком.
3. **Москва доминирует** (10 649 из 10 694), МО — 42 адреса, но именно там нужна
   точность до района области: одноимённые СНТ и посёлки, платные вызовы.
4. **Район по соседям работает, но 181 улица пересекает границы районов** —
   модель уверенности обязательна, тихая подстановка недопустима.
5. **Координат нет ни у одного адреса.** Если появится геокодирование,
   откроются геометрические методы (полигоны районов, реальное расстояние вместо
   разницы номеров) — вероятно, сильнейшее из доступных улучшений точности.
6. **Обучение уже есть, но замкнуто наполовину:** справочник улиц учится из
   DaData (3 028 записей), модель исправлений — из слияний (46 записей), но её
   предсказания никуда не выводятся. Замкнуть цикл «исправление человеком →
   правило → подсказка» — самая дешёвая победа.
7. **Единый источник правил нормализации** вместо трёх копий (§8.5).
8. **Кэш и справочники должны переживать перезапуск** и быть общими для
   экземпляров: сейчас всё in-memory с TTL 3–5 минут.
9. **Инварианты, которые нельзя потерять при переносе:** название организации
   рядом с адресом, а не вместо него (§6.3, §8.1); квартира не относится к
   адресу (§6.1); ПНД ставит человек (§8.3); `organization` ≠ место эвакуации
   (§8.4); номер дома пользователя неприкосновенен (§8.2).
