## 0. Инварианты

Пять правил, добытые авариями (§8 инвентаризации). Они не обсуждаются и
проверяются тестами, которые нельзя удалить:

1. **Ввод пользователя неприкосновенен.** Сервис возвращает предложения с
   уверенностью. Он не изменяет введённое молча — никогда, ни на каком слое.
   *(Причина: §8.2, подмена `7к7` → `7к1`; жалоба, с которой начался разбор.)*
2. **Тождество адреса — по полному разобранному номеру дома**, не по ведущему
   числу и не по строке целиком. Число дома — только предфильтр кандидатов.
   *(§8.2)*
3. **Название организации — рядом с адресом, никогда вместо него.** Поле адреса
   — всегда «улица, дом». *(§8.1: поиск находил 12 вызовов вместо 2763.)*
4. **ПНД устанавливает человек.** Сервис подсказывает, запись не делает.
   *(§8.3)*
5. **Одно правило нормализации — один код.** Ни одной второй копии списка типов
   улиц. *(§8.5: три расходящиеся копии.)*

Плюс два, вытекающие из модели данных:

6. Квартира, подъезд, этаж, домофон — свойства **вызова**, не адреса. Сервис их
   не хранит и не принимает. *(§6.1)*
7. `organization` (что находится по адресу вызова) ≠ место эвакуации. Это
   разные сущности в разных таблицах. *(§8.4)*

## 1. Ключевое архитектурное решение

> **Весь справочник Москвы и Московской области помещается в оперативную память
> одного процесса. Значит на горячем пути не должно быть ни сети, ни диска, ни
> SQL.**

**Измерено 17.08.2026** (`make probe`, подробности — `docs/04-stage0-findings.md`):

| Сущность | Записей (Москва+МО) | Итого |
|---|---:|---:|
| Адресные объекты (улицы, НП, элементы планировки) | 85 222 | |
| Дома (ГАР) | 2 343 349 | |
| Связи административной иерархии | 14 249 523 | |
| **Рабочий набор, худший случай** | | **509 МБ** |
| Он же с фильтрацией иерархии (ожидание) | | ~300 МБ |
| Полигоны районов Москвы + МО (упрощённые) | ~270 | ~6 МБ |
| Наши адреса + частоты вызовов | 10 694 | ~3 МБ |

Замер сделан на обычных Go-строках без пула и mmap — то есть на заведомо
расточительном представлении. Оптимизированный снапшот будет меньше.

Время сборки — 6 мин 40 с. Скачивать при этом приходится 710 МБ, а не 53 ГБ:
архив читается по HTTP Range через оглавление ZIP (§2.1 findings).

Отсюда следует всё остальное: односерверный Go-бинарь без внешних зависимостей
на чтении, атомарная замена снапшота индекса, Postgres только как источник
правды и журнал, внешние API — только в фоновом обогащении.

## 4. Ядро: нормализация и разбор

### 4.1. Пакет `normalize` — единственный источник правды

Претензия §8.5: список типов улиц живёт в трёх местах — SQL-функция
`street_key()`, `normalizeStreetKey()` в `orgMatcher.ts`, `STREET_TYPE_RE` в
`addressService.ts`. Расхождение даёт разный результат в зависимости от того,
кто сравнивал.

Решение: список объявлен **один раз** в Go, а SQL **генерируется** из него.

```go
// internal/normalize/street.go
//go:generate go run ./gen -out ../../sql/normalize.sql

var streetTypes = []streetType{
    {Canon: "улица",      Aliases: []string{"ул", "ул.", "улица"}},
    {Canon: "шоссе",      Aliases: []string{"ш", "ш.", "шоссе"}},
    {Canon: "проспект",   Aliases: []string{"пр", "прт", "пркт", "пр-кт", "проспект"}},
    // ... переулок, площадь, бульвар, набережная, проезд, тупик,
    //     аллея, линия, квартал, микрорайон
}
```

`sql/normalize.sql` содержит `street_key()` и `search_norm()`, собранные из того
же массива, и заголовок `-- CODE GENERATED. DO NOT EDIT.`.
CI падает, если `go generate ./... && git diff --exit-code` даёт изменения.

Контрактный тест: для всех 10 694 улиц из прода `normalize.StreetKey(s)` в Go и
`street_key(s)` в PostgreSQL обязаны совпасть символ в символ. Это исполняемая
версия инварианта 5.

Гарантии, проверяемые property-тестами:

* идемпотентность: `f(f(x)) == f(x)`;
* устойчивость к `ё`/`е`, регистру, порядку слов, отсутствию типа улицы;
* «улица Саляма Адиля» = «Саляма Адиля ул.» = «саляма адиля» (§2.6).

### 4.2. Разбор номера дома — ядро системы

Обоснование приоритета: **6036 адресов из 10 694 содержат кириллицу в номере**,
уникальных написаний — 2034. «Дом = целое число» — неверная модель (§2.3).

```go
// internal/parse/house.go
type House struct {
    Raw string        // ровно то, что ввёл пользователь. НИКОГДА не меняется.

    Kind  HouseKind   // Дом | Владение | Домовладение
    Num   string      // "7", "1/2" (угловой), "15"
    NumN  int         // 7 — только для предфильтра кандидатов (§8.2)
    NumL  string      // литера при номере: "А" в "15А"

    Corpus   string   // "7" в "7к7"
    CorpusL  string
    Building string   // строение: "4" в "10с4"
    Liter    string   // литера: "Г"

    Spans []Span      // привязка каждого поля к [from,to) в Raw
    Flags Flags       // WrongLayout | Homoglyphs | Unparsed | Ambiguous
}

// Каноническая форма для ТОЖДЕСТВА. Не для показа.
func (h House) Canonical() string  // "7к7", "10с4", "вл15А"
// Форма для ПОКАЗА — всегда h.Raw.
```

**Тождество:** `a.Canonical() == b.Canonical()`. Следствия, зафиксированные
тестами: `"7 к 7" == "7к7"`, но `"7к7" != "7к1" != "7"`. Это регресс на §8.2.

Грамматика — конечный автомат по токенам (число, буква, маркер, разделитель).
Маркеры: `к|корп|корп.|корпус`, `с|стр|строение`, `вл|влад|владение`,
`лит|литера`, `д|дом`, `дв|домовладение`. Разбор детерминирован и объясним:
для каждого решения есть спан и правило, которое его породило.

**Гомоглифы.** Латинские `c a k p e o x y B H M T` визуально равны кириллическим.
Диспетчер, не переключивший раскладку, вводит `7r7` («к» в латинской раскладке —
`r`). Нормализация распознаёт оба случая, ставит флаг и **предлагает**
исправление; сама не подставляет (инвариант 1).

Property-тесты: `Canonical(Canonical(x)) == Canonical(x)`; для всех 2034
уникальных написаний из прода разбор не паникует и `Raw` восстановим;
`go-fuzz` на произвольных строках.

### 4.3. Разбор строки адреса

Вход: свободная строка либо структурированные поля. Выход: `ParsedAddress` с
уверенностью по каждому компоненту, спанами и **явным нераспознанным остатком**
(в отличие от сервисов, которые молча выкидывают хвост).

Слои, по порядку и с падающей уверенностью:
раскладка → гомоглифы → населённый пункт в скобках («СНТ Лесная поляна») →
тип улицы префиксом или суффиксом → номер дома → остаток.

### 4.4. Коды качества

Заимствованы у DaData (§2.1 конкурентного анализа), расширены доменными:

```go
type Quality struct {
    Parse    ParseQC     // 0 уверенно · 1 остался хвост · 2 мусор · 3 есть альтернативы
    Street   MatchQC     // 0 точное · 1 префикс · 2 нечёткое · 3 не найдено
    House    HouseQC     // 0 в справочнике · 1 реален, но не в ГАР · 2 не найден
    District Confidence  // high | low | none  + Candidates
    Geo      GeoQC       // 0 точные координаты … 4 до города · 5 нет
    Source   Source      // local | gar | osm | dadata | neighbors | user
}
```

`Source` (провенанс) обязателен на каждом ответе: интерфейс должен уметь
показать, откуда взялось значение, а разбор аварии — восстановить путь.

## 5. Индекс и поиск

### 5.1. Снапшот

Неизменяемая структура, целиком собранная в фоне и подменяемая одним
`atomic.Pointer[Snapshot].Store(next)`. Читатели работают **без блокировок** —
`Load()` и всё. Старый снапшот собирает GC, когда его отпустят последние
запросы.

Свойства: перестройка не влияет на latency чтений; невозможно наблюдать
полусобранное состояние; откат на предыдущий снапшот — один `Store`.

Собирается из: снапшота ГАР (файл `.yfsnap`, mmap), таблицы `addresses`,
выученного словаря, частот вызовов. Полная перестройка — по расписанию и по
сигналу; инкрементальные вставки (новый адрес создан) — в дельта-слой поверх
снапшота, чтобы адрес был находим сразу.

### 5.2. Четыре слоя поиска

| Слой | Структура | Стоимость | Скор |
|---|---|---|---|
| Точное | `map[StreetKey][]ID` | O(1) | 100 |
| Префикс | отсортированный `[]key` + бинарный поиск по границам диапазона | O(log n) | 80 |
| Подстрока | биграммный инвертированный индекс | O(k·postings) | 60 |
| Нечёткое | те же биграммы + верификация Дамерау–Левенштейна | O(кандидатов) | 30 + sim·30 |

Почему биграммный инвертированный индекс, а не SymSpell: словарь ~110 000
названий, SymSpell глубины 2 порождает десятки миллионов ключей удаления и
сотни МБ — цена, не оправданная выигрышем на таком размере. Биграммы дают
кандидатов за микросекунды, а точную дистанцию считаем только на 50–100
финалистах. Порог отсечения — как в текущей системе: Левенштейн ≤ 2 при
ratio ≥ 0.6 либо биграммный Dice ≥ 0.65 для строк от 5 символов (§3.3
инвентаризации) — эти пороги проверены практикой, менять их без замеров нельзя.

Ранний выход: если точный слой дал ≥ `limit` результатов, нечёткий не считается.

### 5.3. Ранжирование — наше главное преимущество

```
score = базовый_скор_слоя
      + w_freq   · log(1 + вызовов_по_адресу)     ← 92 000 вызовов, нет ни у кого
      + w_hist   · история_адресов_пациента       ← §6.2, чипы
      + w_region · (регион == 77 ? 1 : 0)         ← 10 649 из 10 694
      + w_type   · совпал_тип_улицы
      + w_recent · свежесть
```

Веса не константы в коде, а строка в `rank_weights` с версией; подбираются
офлайн на golden-корпусе (`cmd/yfias-replay`) по метрике «букв до правильной
подсказки» — целевое ≤ 2.0 против 2.48 у лучшего конкурента.

Приоритет региона 77 напрямую лечит болезнь «предлагает город вместо улицы»,
отмеченную у DaData, Iqdq и Яндекса.

## 6. Тождество, дедупликация, запись

`Resolve` — единственный путь появления адреса в базе.

```
1. parse(вход)                → ParsedAddress + Quality
2. exact(street_key, house.Canonical())          → попадание? вернуть
3. предфильтр по (street_key, house.NumN)        → кандидаты        ← ТОЛЬКО предфильтр
4. среди кандидатов: Canonical() == Canonical()  → попадание? вернуть
5. policy:
     Strict  — не создавать, вернуть кандидатов (по умолчанию для фоновых задач)
     Create  — создать, обогащение поставить в очередь (интерактивный ввод)
6. INSERT ... ON CONFLICT (street_key, house_canonical) DO UPDATE
     непустое заполняет пустое, заполненное не перетирается
```

Шаг 3 — то самое место, где сломалась старая система. Комментарий в коде и тест
`TestResolve_Issue_8_2_HouseIdentityIsFullCanonical` фиксируют, что `NumN` здесь
и только здесь допустим.

Уникальный индекс переносится со `(street, house)` (текстовое сравнение,
чувствительное к написанию) на `(street_key, house_canonical)` —
детерминированные поля. `street` и `house` остаются как введено пользователем.

**Слияние.** Транзакция: перевод вызовов на целевой адрес → удаление исходных →
событие `merge` в журнал. Отличие от текущего поведения: сервис **предупреждает**,
если сливаемые адреса имеют разные `Canonical()` (то есть, вероятно, это разные
корпуса), но не запрещает — ответственность на человеке. Событие уходит в
`learn` (§8).

## 7. Обогащение: район, ПНД, организация

Порядок источников, каждый со своей уверенностью:

| # | Источник | Уверенность | Когда |
|---|---|---|---|
| 1 | **Point-in-polygon** по границам районов (OSM) | high | есть координаты |
| 2 | Консенсус соседних домов | high/low по правилам §3.2 | нет координат |
| 3 | Nominatim (асинхронно) | low | нет и соседей |
| 4 | DaData (асинхронно) | low | резерв |

Слой 1 — новый и закрывает главную дыру: **181 улица пересекает границы
районов** (§2.3), на них эвристика соседей уверенно врёт. Полигоны решают это
точно и бесплатно.

Логика соседей (`addressNeighbors.ts`, §3.2) переносится **как есть**, это
проверенный код: вес 100 за совпадение числа дома, `max(0, 50−4|Δ|)` за ту же
чётность, `max(0, 20−4|Δ|)` за противоположную сторону, `high` при доле лидера
≥ 0.8 и (вес ≥ 100 или ≥ 2 согласных соседей). Тесты переносятся тоже (13 штук).

При `low` — возвращаются кандидаты, интерфейс показывает чипы «Район · ПНД ?»,
выбирает диспетчер. Тихой подстановки нет (§10.4 инвентаризации).

**ПНД.** Связь «район → ПНД» переводится с текстового `JOIN` (`pnds.dis =
addresses.district`, рвётся на `ё`/`е` — §2.2) на числовой `district_id`.
Запись `pnd_id` — только из явного пользовательского ввода (инвариант 4);
вычисленное значение возвращается как подсказка с `Source: neighbors|geo` и в
базу не пишется.

**Организация.** Отдельное поле в ответе, всегда рядом с `street`+`house`,
никогда вместо (инвариант 3). Сервис отдаёт `{street, house, organization}`
раздельно; склейку в строку делает потребитель. Разделитель ` · ` (U+00B7) для
приложения врача остаётся, но формируется на стороне API-адаптера, а не в ядре.

## 8. Самообучение

Это дифференциатор (§3.3 конкурентного анализа). Механизм — журнал событий и
офлайн-вывод правил.

### 8.1. Журнал

```sql
CREATE TABLE addr_events (
  id           bigserial primary key,
  ts           timestamptz not null default now(),
  kind         text not null,   -- typed|suggested|selected|rejected|corrected|merged|resolved
  session_id   uuid,
  raw_input    text,            -- что печатал человек
  suggestions  jsonb,           -- что показали (id + скор + слой)
  chosen_id    text,            -- что выбрал
  final_street text,            -- что осталось в карте
  final_house  text,
  snapshot_ver int,             -- версия индекса
  weights_ver  int              -- версия весов ранжирования
);
```

Каждое взаимодействие — событие. Это и обучающая выборка, и материал для
разбора аварий, и основа A/B весов.

### 8.2. Что выводится из журнала

| Продукт | Источник | Применение |
|---|---|---|
| Частоты адресов | `resolved` | вес ранжирования |
| Правила исправления | `corrected`, `merged` | подсказка «возможно, вы имели в виду» |
| Синонимы и жаргон | `typed` → `chosen` при низком сходстве строк | «Бауманка» → Басманный, «Склиф» → НИИ Склифосовского |
| Словарь улиц | `chosen` из upstream-подсказок | пополнение справочника |
| Пороги и веса | весь журнал | офлайн-подбор на golden-корпусе |

Модель исправлений (`addressModel.ts`, §3.4) переносится: шесть слоёв,
извлечение правил трансформации из пар «было/стало». Но с двумя изменениями:

1. **Цикл замыкается.** Сегодня модель обучается на слияниях, а её предсказания
   никуда не выводятся (§8.8: «реализовано, но не используется»). В новом
   сервисе `predict` встроен в `validate` и `suggest` — это, по оценке
   инвентаризации (§10.6), «самая дешёвая победа».
2. **Правило автоприменяется никогда.** Оно повышает скор подсказки. Порог
   `support ≥ 3` для показа; правила с высоким влиянием попадают в очередь
   ревью админки. Инвариант 1 не имеет исключений.

### 8.3. Защита от вырождения

Обучение на собственных подсказках — контур положительной обратной связи, и он
умеет закреплять ошибку. Защита:

* правила помечаются версией снапшота и весов; при откате весов откатываются;
* событие `rejected` (человек стёр подставленное) весит **в 3 раза больше**
  подтверждения — отрицательный сигнал дороже;
* метрика `correction_rate` по каждому правилу: если после ввода правила доля
  ручных исправлений на этом адресе выросла — правило автоматически гасится;
* raw-вход хранится вечно и не переписывается, так что любую версию модели
  можно переобучить с нуля.

## 9. Надёжность и производительность

### 9.1. Деградация по слоям

| Отказ | Что перестаёт работать | Что продолжает |
|---|---|---|
| Нет интернета | обогащение района через API | **suggest, parse, validate, resolve — полностью** |
| DaData недоступна | резервное обогащение | всё остальное |
| Nominatim недоступен | координаты новых адресов | район по полигонам и соседям |
| **PostgreSQL недоступен** | запись, resolve с созданием | **чтение целиком: suggest, parse, validate из снапшота** |
| Снапшот ГАР повреждён | подсказки по ГАР | подсказки по своей базе (10 694 адреса) |

Строка «PostgreSQL недоступен → подсказки работают» невозможна в текущей
архитектуре и есть главный выигрыш от снапшота в памяти.

### 9.2. Внешние источники

Только асинхронно, никогда на горячем пути:

* **Circuit breaker** на источник: 5 ошибок подряд → открыт на 30 с →
  полуоткрыт.
* **singleflight** по ключу запроса — одинаковые параллельные запросы
  схлопываются в один.
* **Кэш в PostgreSQL**, а не в памяти: `upstream_cache(source, key, response,
  fetched_at)`. Переживает перезапуск и общий для экземпляров — прямой ответ на
  §8.7 («кэши in-memory на процесс, TTL 3–5 минут, после перезапуска греется
  заново»).
* **Rate limiter** на Nominatim: 1 запрос/с, как требует их политика.
* Очередь обогащения — таблица в Postgres с `FOR UPDATE SKIP LOCKED`, а не
  канал в памяти: переживает рестарт, не теряет задания.

### 9.3. Бюджеты задержек

| Операция | p50 | p99 | Как достигается |
|---|---|---|---|
| `parse` | 20 мкс | 200 мкс | детерминированный автомат, нулевые аллокации на горячем пути |
| `suggest` (в процессе) | 300 мкс | **5 мс** | снапшот в RAM, ранний выход, без сети |
| `suggest` (по HTTP, LAN) | 2 мс | 15 мс | + сериализация и сеть |
| `validate` | 400 мкс | 6 мс | тот же индекс + правила |
| `resolve` (попадание) | 1 мс | 10 мс | одно чтение |
| `resolve` (создание) | 5 мс | 25 мс | одна запись, обогащение в очередь |

Регресс-бенчмарки (`go test -bench`) в CI с порогом: рост p99 более чем на 20% —
красная сборка.

### 9.4. Правила SQL (перенос §5 инвентаризации)

Замеренные последствия нарушений: адресная ветвь 4582 мс → 186 мс; функция
вместо оператора — 476 мс вместо 95 мс; `EXISTS` вместо `LATERAL` — 1017 мс
вместо 95 мс. Правила остаются в силе для всех запросов, которые всё же идут в
базу:

* сравнение дома — по числу через `house_num()`, не строкой;
* только операторы `%`, `<%`, `%>`, **никогда** `word_similarity(...) > x`
  (даёт Seq Scan);
* `JOIN LATERAL` по токенам, не `EXISTS (SELECT … unnest)`;
* отбор по малой таблице до присоединения `calls` (92 тыс.);
* **любая правка поиска сопровождается `EXPLAIN (ANALYZE)` в описании PR** —
  обе ловушки выглядят безобидно.

Тест в CI: `EXPLAIN` ключевых запросов не содержит `Seq Scan` по `calls`.

### 9.5. Наблюдаемость

Prometheus: гистограммы по операциям и слоям поиска, `suggest_layer_hit{layer}`,
`upstream_breaker_state`, `snapshot_age_seconds`, `correction_rate`,
`letters_to_correct_suggestion` (наша целевая метрика полезности), размер
снапшота, GC pause.

`slog` в JSON с `request_id`; при `Quality.Parse >= 2` (мусор) — событие в
журнал для последующего анализа: это будущие правила.

### 9.6. Стек

| Что | Выбор | Почему |
|---|---|---|
| HTTP | `net/http` (Go 1.22+ routing) | роутинг в stdlib, минус зависимость |
| БД | `pgx/v5` напрямую | без ORM: запросы к адресной ветви требуют ручной настройки под планировщик (§9.4) |
| Миграции | `goose`, встроены в бинарь | сейчас накатываются руками, и две числились применёнными, не будучи (§2.5) |
| Логи | `log/slog` | stdlib |
| Метрики | `prometheus/client_golang` | стандарт |
| Трассировка | OpenTelemetry | опционально |
| Тесты | stdlib + `testcontainers-go` | реальный Postgres в интеграционных |
| Сборка | один статический бинарь + `.yfsnap` | деплой копированием, откат — заменой файла |

Отвергнуто: Elasticsearch (Photon/Pelias) — отдельный кластер ради данных,
влезающих в 300 МБ RAM; libpostal через cgo — §3.4 конкурентного анализа;
ORM — конфликтует с §9.4.

## 10. Тестирование

Сегодня тестов нет на `getOrCreate` (включая регресс §8.2), на `validate`, на
`addressModel`, на слияние, на адресную ветвь поиска (§9 инвентаризации). Это
и есть места, где случились все известные аварии. Порядок обратный:

### 10.1. Golden-корпус

`testdata/golden/` — выгрузка с прода, обезличенная:

* 10 694 адреса — разбор, `Canonical()`, `StreetKey()` для каждого;
* 2 034 уникальных написания дома — разбор не паникует, `Raw` восстановим;
* 6 036 адресов с кириллицей в номере — корпус/строение/владение распознаны;
* 1 922 группы «улица + число дома» — **не слиты** (это разные корпуса);
* 81 группа настоящих дублей — **слиты**;
* 181 улица через границы районов — район не выдаётся с `high` без координат;
* 21 адрес с улицей `null null` — распознаны как мусор (`Parse = 2`), не падают.

### 10.2. Регресс-тесты на известные аварии

Каждый именован по параграфу инвентаризации и содержит ссылку на неё:

| Тест | Проверяет |
|---|---|
| `TestIssue_8_1_FullAddressIsNeverOrganization` | поле адреса — улица и дом; поиск «саляма адиля» находит адреса ГКБ № 67 |
| `TestIssue_8_2_HouseIdentityIsFullCanonical` | `7к7` не приклеивается к `7к1` и к `7` |
| `TestIssue_8_3_PndNeverAutoWritten` | `pnd_id` пишется только из явного ввода |
| `TestIssue_8_5_SqlAndGoNormalizeAgree` | Go и SQL совпадают на всех 10 694 |
| `TestIssue_8_6_NoSeqScanOnCalls` | `EXPLAIN` без Seq Scan |
| `TestInvariant_UserInputNeverMutated` | property-тест: `Raw` на выходе == `Raw` на входе, всегда |

### 10.3. Property и fuzz

`Canonical(Canonical(x)) == Canonical(x)`; `StreetKey` идемпотентен и
инвариантен к перестановке слов; `go-fuzz` на парсере — ни паник, ни
экспоненциального времени.

### 10.4. Теневой прогон

`cmd/yfias-replay` прогоняет журнал реальных запросов через старую и новую
систему и печатает расхождения по классам. Условие выхода на прод: расхождений
класса «новая нашла хуже» — ноль; класса «новая нашла лучше» — сколько угодно.

## 11. Открытые решения владельца

Не технические, требуют решения до этапа 2:

1. **Полнота ГАР.** Загружать Москву + МО (~300 МБ RAM, ~4 ГБ на диске под
   исходники) или всю РФ (36 ГБ архива, ~300 ГБ распакованного XML)? Данные
   инвентаризации (10 649 из 10 694 — регион 77) говорят за первое, с
   возможностью добавить регион конфигурацией. **Рекомендация: Москва + МО.**
2. **Владение данными.** Сервис становится владельцем таблицы `addresses`
   (МИС хранит только `address_id`) или читает её как реплику? **Рекомендация:
   владелец, но поэтапно — см. `03-roadmap.md`, этапы 3–5.**
3. **Автозаполнение ПНД.** Сегодня 1684 из 10 694 (16%). Если сервис начнёт
   подставлять ПНД автоматически, изменятся цифры в отчётах по ПНД (§8.3). Это
   решение владельца, не техническое. **Рекомендация: не менять поведение**,
   отдавать подсказку в интерфейс.
4. **DaData: остаёмся ли платными.** После загрузки ГАР офлайн DaData нужна
   только как резерв на адреса вне справочника. **Рекомендация: оставить на
   бесплатном тарифе, вне горячего пути.**
