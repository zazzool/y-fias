# Теневой режим: что добавить в МИС

Этап 3 плана. Сервис работает **рядом** с существующим бэкендом, его ответы
игнорируются, расхождения записываются. Решение «идти дальше» принимается на
неделе реальных данных, а не на вере в дизайн.

Риск нулевой: прод не изменяется, а теневой вызов не способен повлиять на
основной путь.

---

## Почему сравнение делаем мы, а не МИС

Классификация расхождений — самая содержательная часть теневого режима, и её
надо покрывать тестами, а не наблюдать в чужих логах. Поэтому МИС присылает
**запрос и свой ответ**, а сравнение, классификацию и запись делает Y-FIAS.

Правка чужого репозитория сводится к вызову «отправь и забудь».

---

## Что добавить в `web/ponp.psync.ru`

Один файл и один вызов.

### `server/utils/yfiasShadow.ts`

```ts
/**
 * Теневая отправка адресных запросов в Y-FIAS.
 *
 * Вызов НЕ ДОЛЖЕН влиять ни на что: ответ игнорируется, ошибки
 * проглатываются, таймаут жёсткий. Если Y-FIAS недоступен, медленен или
 * отвечает мусором, диспетчер этого не замечает.
 */
const YFIAS_URL = process.env.YFIAS_URL || ''
const YFIAS_API_KEY = process.env.YFIAS_API_KEY || ''  // роль client
const TIMEOUT_MS = 50

type ShadowPayload = {
  method: 'suggest' | 'house'
  query?: string
  house?: string
  legacy?: string[]
  legacy_canonical?: string
  chosen?: string
  region?: string
  session_id?: string
}

export function shadowCompare(payload: ShadowPayload): void {
  if (!YFIAS_URL || !YFIAS_API_KEY) return

  // Никакого await: теневой вызов не должен добавлять ни миллисекунды
  // к ответу диспетчеру.
  const ctrl = new AbortController()
  const timer = setTimeout(() => ctrl.abort(), TIMEOUT_MS)

  fetch(`${YFIAS_URL}/v1/shadow`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', 'X-API-Key': YFIAS_API_KEY },
    body: JSON.stringify(payload),
    signal: ctrl.signal,
  })
    .catch(() => {})       // недоступность Y-FIAS не является событием для МИС
    .finally(() => clearTimeout(timer))
}
```

### Точки вызова

| Где | Что передавать |
|---|---|
| `addressService.suggest`, после формирования ответа | `method: 'suggest'`, `query`, `legacy` — названия из ответа по порядку |
| `addressService.getOrCreate`, после `formatHouseCanonical` | `method: 'house'`, `house` — сырой ввод, `legacy_canonical` — результат |
| SPA, при выборе подсказки (`onStreetSelected`) | тот же `suggest`-вызов плюс `chosen` |

Третья строка важнее первых двух. **Выбор человека — единственный
объективный судья:** не «чей список красивее», а «чей список содержал нужное и
выше». Без него сравнение вырождается в спор о вкусах, и Y-FIAS честно
отвечает `differ` вместо `better`/`worse`.

## Как читать результат

### Метрики

```
yfias_shadow_verdicts_total{verdict="same"}
yfias_shadow_verdicts_total{verdict="better"}
yfias_shadow_verdicts_total{verdict="worse"}    <- условие выхода
yfias_shadow_verdicts_total{verdict="differ"}
```

**Условие выхода этапа 3 одно: `worse` равно нулю.** Класса `better` может
быть сколько угодно.

### Разбор расхождений

Каждое сравнение попадает в журнал:

```sql
SELECT raw_input,
       meta->>'verdict'     AS вердикт,
       meta->>'reason'      AS причина,
       meta->>'legacy_top'  AS "прежняя",
       meta->>'ours_top'    AS "наша",
       meta->>'legacy_rank' AS "позиция у прежней",
       meta->>'ours_rank'   AS "позиция у нас"
  FROM addr_events
 WHERE kind = 'shadow' AND meta->>'verdict' = 'worse'
 ORDER BY ts DESC;
```

Блокирующие расхождения пишутся ещё и в лог сервиса на уровне WARN, чтобы
они были заметны сразу, а не всплыли в недельном отчёте.

### Классы вердиктов

| Вердикт | Смысл |
|---|---|
| `same` | ответы совпали по существу; разное написание одной улицы сюда же |
| `better` | мы предложили выбранное, прежняя нет, либо у нас оно выше |
| `worse` | **блокирующий**: выбранного у нас нет или оно ниже |
| `differ` | ответы разные, но судить не о чем — выбор человека неизвестен |

Отдельно про `differ` у номеров домов: он означает, что каноническая форма
разошлась. Это опаснее расхождения подсказок — форма определяет **тождество**
адреса (§8.2), и при переключении записи (этап 5) расхождение решит, слипнутся
адреса или продублируются. Такие случаи разбираются поштучно.

## Чтение отчёта из МИС

Разбирать расхождения в `psql` можно ровно до первой недели реальной нагрузки.
Дальше нужен список, в котором видно, что уже разобрано, — иначе условие «ноль
`worse`» недостижимо: часть расхождений всегда окажется ложной (диспетчер
выбрал не ту улицу, промахнулся мимо строки), и без пометки такие случаи будут
держать счётчик ненулевым вечно.

Поэтому сервис отдаёт журнал наружу, а МИС показывает его на странице
«Адресные системы» (`/admin/address-shadow`, только администратор).

| Метод | Что делает |
|---|---|
| `GET /v1/shadow/report` | сводка: классы, ряд по времени, причины, качество ранжирования, состояние условия выхода |
| `GET /v1/shadow/cases` | отдельные сравнения с фильтрами (`days`, `method`, `verdict`, `review`, `q`) и пагинацией |
| `POST /v1/shadow/review` | отметка о разборе: `open`, `accepted`, `fixed`, `false_alarm` |

Отметки живут в отдельной таблице `shadow_reviews`. Журнал `addr_events` не
переписывается: он сырой и неизменяемый (§8.1 архитектуры), а решение человека —
отдельный факт с отдельным временем и автором.

### Качество ранжирования

Отчёт считает по выбору человека четыре величины для каждой из систем:

| Величина | Смысл |
|---|---|
| доля попаданий | выбранное вообще было в выдаче |
| первое место | выбранное стояло первым |
| MRR | средний обратный ранг: 1.0 — всегда первое, 0 — не было вовсе |
| средняя позиция | считается **только по попаданиям**: промах — не «последнее место» |

В один индекс они не сводятся намеренно. Система, которая всегда находит, но
кладёт нужное пятым, и система, которая половину не находит, а половину ставит
первой, дали бы одинаковый общий балл и требуют разного лечения.

### Проверка выхода

`gate` в ответе `/v1/shadow/report` отвечает на вопрос «можно ли дальше» и
называет причину отказа. Условий три, и второе часто забывают:

1. неразобранных `worse` — ноль;
2. выборка не меньше 500 сравнений: ноль расхождений на двух десятках запросов
   означает отсутствие данных, а не готовность;
3. есть хотя бы одно сравнение с выбором человека — иначе судить не о чем.

---

## Условия выхода этапа 3

1. Неделя теневой работы под реальной нагрузкой.
2. Расхождений класса `worse` — **ноль**.
3. Ни одного 5xx и ни одного всплеска задержки у основного бэкенда.
4. Отчёт по расхождениям разобран, каждое объяснено.

Это точка, где решение идти дальше принимается на данных.
